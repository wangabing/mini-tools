## Context

项目是 Next.js App Router 应用，当前所有业务计算都在浏览器内完成，没有应用服务器、数据库或账号系统。用户希望先用免费的公开地址上线，同时通过 `mrwbz@sina.com` 接收问题与建议。GitHub Pages 只能托管静态文件，不能运行 Next.js API 路由，因此留言接收与页面托管需要解耦。

联系页的对象是国内个体商家和新手卖家，页面的单一任务是让用户用很少的信息说清问题，并清楚知道如何获得回复。视觉继续使用现有矿物白、碳黑、账本青绿与数据靛蓝，采用“公开联络线 + 留言工作面”的左右布局，不引入新的视觉系统或组件库。

## Goals / Non-Goals

**Goals:**

- 在无自建后端时提供可用的邮箱联系和在线留言。
- 保持表单简短、可访问，并提供发送中、成功、失败和未配置状态。
- 保证留言不包含或读取计算器中的售价、成本、费率和利润结果。
- 让项目通过 GitHub Actions 静态导出到 GitHub Pages，并正确处理项目站点子路径。
- 提供可以由非开发人员照做的上线、配置、检查和回滚文档。

**Non-Goals:**

- 不实现自建管理后台、SQLite 留言表、登录、附件上传或工单系统。
- 不承诺留言服务永久免费、在中国大陆所有网络环境都稳定，或邮件必然进入收件箱。
- 不在本次变更中购买域名、接入广告、部署数据库或收集计算器数据。

## Decisions

### 1. Cloudflare Pages 作为商业运营首选，GitHub Pages 作为备选

`STATIC_EXPORT=true` 时启用 Next.js `output: "export"` 和尾斜杠，供 Cloudflare Pages 等静态主机使用；日常本地开发与常规 Node.js 构建保持原状。`GITHUB_PAGES=true` 同样启用静态导出，并从 `GITHUB_REPOSITORY` 推导项目站点的 `basePath`；用户名/组织名站点仓库以 `.github.io` 结尾时使用根路径。

Cloudflare Pages 免费提供 `pages.dev` HTTPS 地址，支持 GitHub 自动部署和商业静态站点，适合当前广告变现方向。GitHub Pages 技术上可以承载应用，但官方限制明确说明其不允许被用作在线业务、电商站点或商业 SaaS 的免费主机，因此只保留为非商业预览或短期技术验证。Vercel Hobby 同样限制为非商业个人使用，不作为广告站点的免费方案。

### 2. Formspree 作为留言交付服务

客户端把 `name`、`email` 和 `message` 通过 `fetch` 提交到构建时注入的 `NEXT_PUBLIC_FEEDBACK_ENDPOINT`，使用 JSON 响应在原页面展示状态。端点属于公开配置，不作为密钥；收件邮箱在 Formspree 控制台绑定并验证为 `mrwbz@sina.com`。

选择原因是它支持静态网站、无需部署 API、免费方案足以做早期验证，并带基础垃圾信息过滤。直接 `mailto:` 无法提供稳定的页面内提交体验；自建 Serverless Function 会增加供应商配置、滥用防护与运维责任；Google Forms 会把用户带离产品体验。

### 3. 始终保留直接邮件退路

联系页公开展示邮箱。端点缺失时不显示可提交的在线表单，而是说明当前可直接发邮件；网络错误或服务拒绝时保留用户填写的内容，并提供带主题的邮箱链接，避免误导用户以为消息已送达。

### 4. 留言与计算数据严格分离

表单组件没有访问计算器状态、URL 参数或本地存储的逻辑，只发送用户在联系页主动填写的三个字段和固定主题。隐私页面分别说明本地计算和主动留言的处理方式，避免把“所有内容都不上传”的旧承诺错误扩展到留言。

### 5. 最小表单与安静的防滥用

留言内容必填，称呼和回复邮箱选填；回复邮箱使用浏览器原生格式校验。表单加入一个对正常用户隐藏的诱饵字段，命中时不发送网络请求。服务方的基础垃圾信息过滤仍是主要防护，达到免费额度或流量增长后再评估升级或自建接口。

## Risks / Trade-offs

- [Formspree 免费方案每月提交量和留存有限] -> 文档记录当前公开额度与核对日期，始终保留直接邮箱，并在上线后监控用量。
- [Formspree 或 Sina 邮箱可能被网络、反垃圾策略影响] -> 上线后执行真实收件测试，检查垃圾箱，并把失败状态设计成可操作的邮件退路。
- [公开邮箱可能收到垃圾邮件] -> 在线表单端点不暴露收件地址，但用户要求展示邮箱；建议使用邮箱规则和独立文件夹管理。
- [GitHub Pages 商业使用受官方条款限制] -> 商业运营使用 Cloudflare Pages；仅在用途符合 GitHub 条款时启用 Pages 工作流。
- [GitHub Pages 项目站点使用子路径] -> 使用 `basePath`、Next `Link`、构建时站点 URL 和清单作用域，并在导出产物中检查资源地址。
- [GitHub Pages 没有服务端安全头和动态能力] -> 当前功能保持纯静态；需要数据库或服务端接口时迁移到支持运行时的平台。
- [公开仓库会暴露源码] -> GitHub Free 的 Pages 可从公开仓库部署；若必须保持源码私有，应先核对账户计划或改用其他托管平台。

## Migration Plan

1. 合并联系页、静态导出配置、工作流与文档，先保持留言端点未配置。
2. 在 Formspree 创建表单并验证 `mrwbz@sina.com`，记录表单端点。
3. 在 Cloudflare Pages 连接 GitHub 仓库，配置静态导出、公开站点 URL 和表单端点，运行首次部署。
4. 用 `pages.dev` 地址检查全部路由、资源、留言成功与收件、移动端布局和隐私文案。
5. 回滚时重新部署上一个提交；若只需停用在线留言，删除仓库变量并重新构建，邮箱入口仍可用。

## Open Questions

- 当前远程仓库为 `wangabing/mini-tools`；Cloudflare Pages 项目名和最终 `pages.dev` 地址仍需由用户在控制台确认。
- Formspree 表单端点必须由邮箱所有者登录创建并完成验证，当前源码只能预留配置位。
