# 无商家招募条件下的公开证据验证方案与首轮结果

> 版本：1.0  
> 更新日期：2026-10-10  
> 执行状态：已完成首轮定向检索、来源核对和合成场景复算  
> 适用边界：公开资料研究与工程验证，不属于本产品真实用户反馈

## 1. 执行决定

暂时无法招募 10—15 位商家，不再作为开发和发布前的必备条件。采用“官方规则与入口 → 专业社区原文 → 文献与行业研究 → 独立场景复算 → 产品需求与验收”的证据链推进。

AI负责检索整理、主题编码、发现矛盾、提出假设和生成待审核案例。所有结论必须能回到已读取的原文或独立计算依据；AI角色扮演不计为商家访谈，文章篇数不计为用户人数。

本方案与 [产品评审与阶段规划](product-review-and-planning.md) 配套。现有计算能力继续由领域测试验证，研究发现转化为后续产品修复，不直接自动改写平台费率。

## 2. 可以替代和不能替代的验证

| 验证问题 | 公开资料和AI可承担的工作 | 仍然未知的部分 |
| --- | --- | --- |
| 需要哪些成本字段 | 根据官方规则、从业经验和研究整理候选字段 | 目标用户最常用字段及实际填写困难 |
| 计算口径是否自洽 | 独立算例、边界分析、正反向闭环与敏感性分析 | 未公开合同条款和个店账单适配 |
| 哪些问题值得优先处理 | 对不同原始来源做主题编码和证据对照 | 目标商家总体中的痛点发生比例 |
| 界面能否完成任务 | 基于明确任务作启发式评审和浏览器流程检查 | 真实首次使用耗时、理解错误与满意度 |
| 是否会持续使用或付费 | 整理候选价值主张和设计可试用版本 | 留存率、转化率、真实付费意愿 |

后两类商业指标标记为“待观测”，不填写AI估计值。可以在这些指标未知时继续建设和提供试用，但不能宣称已验证市场需求。

## 3. 平台优先顺序

首轮选择淘宝／天猫货架经营与抖音内容成交两类路径；第三个平台待官方规则可访问性或明确模型差异出现后再选。优先理由是现有模板基础和成本模型差异，不是已发现目标用户需求集中在这些平台。

不要求每个平台收集相同数量的文章。优先补齐收入、计费基数、退款处理、达人／广告和固定成本的证据缺口。后台或合同才可取得的信息继续保留“待核对”，不以历史媒体费率或AI推断填补。

## 4. 来源与结论管理

### 4.1 来源分层

1. **官方规则正文**：仅在明确适用主体、类目、交易状态、生效时间和计费基数时，才可支持对应规则结论。官方首页及文章标题只能作为入口。
2. **专业社区与媒体原文**：支持发现痛点、字段和历史政策线索；不能据此确认当前有效费率或行业均值。
3. **论文与行业研究**：支持模型结构和机制讨论；标明仅读摘要、落地页或全文，不外推其地域、年代及样本比例。
4. **合成案例**：只验证已声明假设下的算术与模型，不是经营观测。

相同采访、报告或转载链视为一个原始来源。多个网站转载同一文章不能提高独立证据数量。本轮三篇社区文章均来自人人都是产品经理，原始作者／媒体不同，但仍存在单一分发平台及搜索主题选择偏差。

### 4.2 证据记录

每条来源记录原始URL、最终URL、标题、来源类别、发布时间、抓取时间、内容哈希、短摘录、支持结论、适用边界及独立来源组，见 [证据登记表](research/public-evidence.json)。

HTTP 200不代表已取得正文；登录页、动态外壳和错误页不计为有效规则证据。失效链接和访问失败照实记录。完整网页仅作本地临时核对，仓库保留短摘录与引用，不发布全文转载。

### 4.3 获取与更新方式

本轮使用定向HTTP读取公开页面和公开搜索接口，再核对原文；没有运行全站爬虫、登录后台或采集私密商家资料。已完成的查询与读取不涉及向社区发帖或联系作者。

持续研究按登记表URL定向复核，先读取公开页面、检查最终跳转和正文，再更新结论。批量采集应检查站点的公开抓取约束，限制请求频率；遇到登录、验证码和不可访问页面时记录缺口，不绕过访问限制。

费用规则至少每90天复核一次，发现政策变更立即复核。历史文章保留原始年代，不能通过重新抓取将其变成当前政策。只有已核验的具体规则才能更新业务预设。

## 6. 独立案例库与实际引擎复算

已建立 [14个合成场景](research/profit-scenarios.json)，覆盖基础订单、折扣、混合计费基数、补贴、达人费用、月费、零订单、极端费率、定价反推、退货回收和交易费不退。

运行实际领域引擎：

```bash
node scripts/audit-profit-scenarios.mjs
```

生成 [复算结果](research/profit-scenario-results.md)。当前结果为：**8个场景一致，6个退货场景存在口径差异**。

例如S09：售价100元、商品成本60元、10%订单全额退款且货品完整回收，无其他支出。每笔发出订单预期利润36元，现有引擎返回40元。S13进一步呈现退款后不退交易费的重复扣除风险，需要联同收入口径校准。

案例金额与费率全部人为设定，预期值通过独立分支算术给出，不使用当前引擎自行生成。差异说明口径需要决策，不能称为实际商家账单误差。

审计命令默认退出成功只表示完成分析；若需将所有案例一致作为自动检查，可运行：

```bash
node scripts/audit-profit-scenarios.mjs --strict
```

当前严格模式预期退出1，直至退货口径明确并校准引擎或案例适用范围。不得仅为使检查通过而复制当前输出为预期值。

## 7. 调整后的阶段验收

| 阶段 | 可独立执行的验收门槛 | 暂不能证明的指标 |
| --- | --- | --- |
| A：可信度校准 | 定义订单与退货口径；支持范围内独立场景一致；所有差额有处置结论；关键输入和确认失效流程通过检查 | 所有商家账单均已适配 |
| B：复用闭环 | 保存、复制、比较、恢复可完整操作；核算版本和确认状态可追溯；启发式与浏览器任务检查完成 | 回访率、满意度和真实任务耗时 |
| C：经营效率 | 批量导入导出及模拟场景结果可重现；异常输入有提示；形成可试用版本 | 持续使用频率与实际节省时间 |
| D：付费验证 | 可提供明确价值与范围的试用方案；实施付费能力按反馈投入 | 未发生真实交易前不能声称付费需求已验证 |

真实用户和脱敏账单未来获得时再补入证据库，无须预先凑足人数。若一直无法取得用户反馈，仍可完成工程建设和公开试用，但商业有效性保持未验证状态。
