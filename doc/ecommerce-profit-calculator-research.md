# 电商利润计算器：开源项目调研与工程决策

> 调研日期：2026-10-03  
> 文档用途：作为新建“电商工具站”工程的背景资料、技术选型依据和首版开发边界。

## 1. 项目目标

建设一个面向电商卖家的工具网站，首款工具为“电商利润计算器”。网站完成首版上线后，将持续增加相关工具和内容页面，通过搜索流量、自然传播和广告获得收入。

这个产品与现有历史内容应用没有业务关联。需要复用的是 React、TypeScript、测试和工程实践，而不是现有页面、SQLite 内容服务或领域组件。

长期形态预计包括：

- 电商利润计算器
- 平台费率计算器
- 目标利润反推售价
- 盈亏平衡 ROAS
- 最大可承受获客成本
- 折扣影响计算器
- 退货和退款成本计算器
- Amazon、Etsy、eBay、Shopify 等平台专题工具
- 与计算器配套的费率说明、定价指南和案例内容

## 2. 核心结论

### 2.1 不应原样使用某个开源项目上线

调研范围内没有一个项目同时满足以下生产要求：

- 计算公式可靠且有充分测试
- 平台费率有来源、生效日期和更新机制
- 支持地区、币种、税费和平台分类差异
- 适合中文用户或目标市场
- SEO、广告、隐私和品牌配置可以直接使用
- 有足够的社区验证和持续维护记录

部分项目可以直接运行或部署，但“可以运行”不等于“可以作为商业产品直接上线”。

### 2.2 新建独立工程，不继续扩展现有工程

电商工具站应使用独立 Git 仓库和独立部署链路。现有工程的启动过程依赖 SQLite 内容加载，Vite 配置也绑定了内容服务插件；页面、样式和组件高度属于历史阅读业务。

如果继续共用现有工程，会产生以下长期问题：

- 工具页面被无关的 SQLite 和内容 API 依赖牵制
- 两个产品共享构建、发布和故障范围
- 全局样式与领域组件容易互相影响
- SEO、广告审核、统计和隐私配置难以独立管理
- 无法按照工具站的节奏快速增加页面和发布版本

最终决策：**代码重新起步，工程经验选择性复用，业务、仓库和部署完全隔离。**

### 3.1 SellerToolSuite

这是最接近目标商业形态的项目。仓库包含 Amazon、Etsy、eBay、Shopify、Mercari、Poshmark、Facebook Marketplace 等平台的利润、费率、定价、广告 ROI、退货、库存和物流工具。

已具备的能力：

- Next.js App Router 工程
- 约 221 个工具或内容页面
- sitemap
- AdSense 元数据和 `ads.txt`
- 多个平台的工具目录
- 可在 Vercel 上部署

需要二次开发：

- 中文化、人民币和目标地区适配
- 替换原域名、品牌、作者和 AdSense Publisher ID
- 重写隐私政策、使用条款和免责声明
- 将散落在各页面中的公式抽成统一领域模块
- 增加计算公式、费率和边界值测试
- 重写 SEO 内容，避免复制页面形成重复或低质量内容
- 增加费率来源、生效日期、版本和更新流程

成本估算：

- 仅部署并替换品牌：约 1-3 人日
- 改造成可靠的首款中文计算器：约 5-8 人日
- 审核并重构为完整多平台工具站：约 15-30 人日

主要风险：

- 0 Star，社区验证不足
- 约 20 次提交，单人维护，维护历史较短
- 248 个文件中未发现自动化测试
- 页面数量很多，但存在公式和内容高度重复的问题
- 原项目的 AdSense ID、域名和 SEO 内容不能直接沿用

判断：**可以作为信息架构和 SEO 页面组织方式的参考，也能直接部署原型，但不应整体复制后直接投放。**

### 3.2 marketplace-fee-data

这是一个零依赖的费率数据包，已发布到 npm，调研时版本为 `1.0.2`。它提供 Etsy、eBay、Depop、Vinted、Poshmark、Mercari、Whatnot、Gumroad、Patreon 和 DoorDash 等平台的基础费率。

已具备的能力：

- 独立 JSON 费率数据
- JSON Schema
- TypeScript 类型声明
- `feeOn`：计算平台费用
- `breakdown`：计算收入、费用、成本和利润率
- `priceForNet`：按目标净利润反推售价
- 12 个无框架测试
- 每个平台附有官方费率来源链接和注意事项

需要二次开发：

- 完整的工具页面、结果解释和 SEO 内容
- 分类费率、阶梯费率和订单阈值模型
- 国家、地区和币种差异
- VAT、GST、销售税和价内税/价外税模型
- Amazon FBA 配送费、仓储费等非百分比费用
- 中国或东南亚平台费率
- 数据生效日期、过期提醒、审核状态和历史版本

成本估算：

- 接入现有 React 工程并建立基础计算模块：约 1-2 人日
- 连同页面和测试完成首款工具：约 3-5 人日
- 做成可信的多平台首发版本：约 6-10 人日

主要风险：

- 0 Star，依赖单一维护者
- 当前计算模型主要是“百分比 + 固定金额”
- 平台复杂规则有时只存在于备注中，计算函数并未执行这些规则
- 默认数据偏美国市场和美元
- 平台费率随时可能变化，不能无审核地自动使用

判断：**这是三个候选中最适合实际纳入新工程的部分，但应把它视为数据结构和初始资料，而不是最终权威费率系统。**

### 3.3 Profit-Calculator

这是一个通用电商利润计算器，功能与首版需求比较接近。

已具备的能力：

- 产品、运费、包装、营销、平台费和其他成本输入
- 税费开关
- 利润、利润率和推荐售价
- INR、USD、EUR、GBP 多币种显示
- 浏览器本地历史记录
- PDF 导出
- 基础 Meta、Open Graph 和 JSON-LD

需要二次开发：

- 将 PHP/Vanilla JavaScript 页面迁移为 React/TypeScript
- 明确收入、税费、折扣、退款和运费口径
- 重写目标利润售价和盈亏平衡公式
- 增加单元测试、异常值处理和精度策略
- 将 Tailwind、Font Awesome、jsPDF 从 CDN 依赖改为受控构建依赖
- 增加平台费率预设和人工覆盖机制

已发现的计算问题：

- “盈亏平衡销量”只返回 `1` 或 `Never`，不是真正的盈亏平衡分析
- 目标利润售价计算把当前售价产生的平台费当成固定成本，反推逻辑不严谨
- 税费属于含税价还是价外税没有清晰定义
- 没有自动化测试验证结果
- 仓库填写的在线 Demo 在调研时返回 404

成本估算：

- 原样部署到 PHP 主机：少于 1 人日
- 迁移到 React/TypeScript 并修正公式：约 4-7 人日
- 增加平台预设、测试和生产 SEO：约 7-12 人日

判断：**适合作为输入项和交互流程参考，不应继承其核心计算逻辑。**

## 4. 未入选项目说明

### Umair706/amazon-omniscient

该项目调研时有 35 Star，更新至 2026-10-01，是候选中 Star 较高且较活跃的项目。但它是 Amazon FBA 产品研究平台，采用 FastAPI、Next.js 和 AI 相关能力，远超单页工具所需范围；GitHub 许可证识别结果为 `NOASSERTION`，不适合作为商业项目的直接基础。

### bhavman2/fba-calculator

该项目有 15 Star 且使用 MIT 许可证，但最后推送时间为 2019-03-26。Amazon 费率变化频繁，旧代码的 Star 不能抵消费率过期风险，因此未进入最终三项。

### 其他近期项目

搜索结果中存在不少 2026 年更新的计算器，但多数只有 0 Star、没有许可证或只有单个 HTML 页面。没有许可证的公开代码默认不能安全地复制、修改并用于商业产品，只能作为功能调研参考。

## 5. 新工程技术建议

### 5.1 推荐技术栈

```text
框架：Next.js + React + TypeScript
部署：Vercel
样式：CSS Modules、Tailwind CSS 或项目自有设计系统，三者择一
计算：纯 TypeScript 领域模块
单元测试：Vitest
端到端测试：Playwright
数据：首版使用受版本控制的静态费率数据
数据库：首版不需要
账号系统：首版不需要
```

选择 Next.js 的主要原因：

- 每个计算器可以拥有独立且可索引的 URL
- 容易生成页面标题、描述、Canonical 和结构化数据
- 支持静态生成工具页和指南页
- 便于生成 sitemap 和 robots 配置
- 适合逐步扩展长尾关键词页面
- 与 React/TypeScript 开发经验兼容
- 可以低成本部署在 Vercel

### 5.2 建议目录边界

```text
ecommerce-tools/
├── app/
│   ├── calculators/
│   │   └── ecommerce-profit/
│   ├── guides/
│   ├── privacy/
│   └── terms/
├── src/
│   ├── domain/
│   │   └── profit/
│   ├── data/
│   │   └── platform-fees/
│   ├── components/
│   └── analytics/
├── tests/
│   ├── unit/
│   └── e2e/
└── public/
```

关键边界：

- 公式不得直接写在 React 页面组件中
- 页面只负责收集输入、展示结果和解释计算口径
- 费率数据与计算逻辑分离
- 每条平台费率应记录来源、生效日期、适用地区和审核状态
- 用户必须能够手工覆盖平台预设费率
- 首版计算全部在浏览器完成，不收集用户经营数据

## 6. 首版功能范围建议

### 6.1 输入

- 商品售价
- 买家支付的运费
- 折扣金额
- 商品采购或生产成本
- 头程或入库成本
- 包装成本
- 实际发货成本
- 平台佣金百分比
- 支付手续费百分比和固定手续费
- 单笔广告或获客成本
- 预计退货/退款损失
- 税费
- 其他单笔成本

### 6.2 输出

- 订单总收入
- 平台费和支付手续费
- 总成本
- 单笔贡献利润
- 利润率
- 投资回报率 ROI
- 盈亏平衡售价
- 盈亏平衡 ROAS
- 最大可承受获客成本
- 按月销量计算的利润预测
- 成本构成和利润变化解释

### 6.3 首版暂不包含

- 用户注册和登录
- 云端保存计算记录
- 支付或订阅
- 自动抓取平台费率
- ERP 或店铺 API 集成
- 多人协作
- 后台内容管理系统
- AI 定价建议

## 7. 公式与数据质量要求

上线前至少需要验证以下场景：

- 所有输入为零
- 零售价但存在成本
- 亏损订单
- 平台费达到边界值
- 百分比费用和固定费用同时存在
- 买家支付运费与实际运费不同
- 含税价和价外税分别计算
- 高退货率导致利润转负
- 目标利润反推售价后重新正向计算，结果可以闭环
- 小数金额的舍入规则稳定

每个平台预设应显示：

- 数据来源 URL
- 适用国家或地区
- 费率生效日期
- 最后审核日期
- 未覆盖的例外条件
- “结果仅供估算”的声明

## 8. SEO 与广告边界

广告不是首版页面结构的中心。首先需要保证计算器可用、页面速度、内容可信度和搜索意图匹配。

上线基础要求：

- 每个工具一个稳定 URL
- 唯一的标题、描述、正文和 FAQ
- Calculator 或 WebApplication 结构化数据
- sitemap、robots.txt 和 Canonical
- 隐私政策、使用条款和免责声明
- 广告和统计脚本延迟加载
- 不让广告遮挡输入区、结果区或主要操作
- 对需要同意的 Cookie 和个性化广告提供合规处理

不要批量发布只有关键词不同、内容基本相同的计算器页面。大量薄内容可能影响搜索表现和广告平台审核。

## 9. 新工程启动决策

新工程可以直接采用以下决策：

1. 创建独立 Git 仓库，不改造现有历史内容工程。
2. 使用 Next.js、React 和 TypeScript。
3. 首版只做一个高质量的通用电商利润计算器。
4. 不引入数据库、登录、支付或 AI。
5. 计算公式使用纯 TypeScript，并优先完成单元测试。
6. 参考 SellerToolSuite 的页面体系，但不复制其整站代码和 SEO 内容。
7. 参考 marketplace-fee-data 的数据结构和来源记录方式，并扩展复杂费率模型。
8. 参考 Profit-Calculator 的输入与结果布局，但重写公式。
9. 在确定目标用户市场后，再决定首批平台预设。

## 10. 尚待确认的产品问题

开始实现前需要确定：

- 首要用户是国内平台卖家、跨境平台卖家，还是独立站卖家
- 首发语言是简体中文、英文，还是双语
- 首发默认币种和税费规则
- 首批平台预设名单
- 主要搜索市场和部署域名
- 首版是否需要导出、分享链接或本地历史记录

这些选择会直接影响计算模型、费率数据、SEO 关键词和内容规划，应该在编码前形成明确的产品范围。
